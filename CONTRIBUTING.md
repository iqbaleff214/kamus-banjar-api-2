## How Can I Contribute?

### Reporting Bugs

Open a [Bug Report](https://github.com/iqbaleff214/kamus-banjar-api-2/issues/new?template=bug_report.yml). Include:
- Go version and OS
- Steps to reproduce
- Expected vs. actual behavior
- Relevant logs or error messages

### Suggesting Features

Open a [Feature Request](https://github.com/iqbaleff214/kamus-banjar-api-2/issues/new?template=feature_request.yml). Describe:
- The problem you are trying to solve
- Your proposed solution
- Alternatives you have considered

### Improving Dictionary Data

If you find incorrect or missing entries in the Banjar dictionary data, open an issue with the label `data` and describe the correction with a reference source where possible.

### Code Contributions

Before submitting a large PR, open an issue first to discuss scope and approach. Small fixes and documentation improvements can go straight to a PR.

## Development Setup

### Prerequisites

- [Go 1.25+](https://go.dev/dl/)
- [Docker](https://docs.docker.com/get-docker/) and [Docker Compose](https://docs.docker.com/compose/)
- [sqlc](https://sqlc.dev) (for regenerating queries after SQL changes)
- [golang-migrate CLI](https://github.com/golang-migrate/migrate/tree/master/cmd/migrate)

### Local setup

```bash
git clone https://github.com/iqbaleff214/kamus-banjar-api-2.git
cd kamus-banjar-api-2

cp .env.example .env
# Edit .env with your local values

docker compose up -d        # Start PostgreSQL and Redis
make migrate-up             # Apply migrations
make seed                   # Import dictionary seed data
make run                    # Start API with hot-reload (Air)
```

The API will be available at `http://localhost:8080`.

## Running Tests

```bash
make test
# or
go test ./... -count=1 -race
```

Tests are organized by layer:

| Layer | Location | Dependencies |
|---|---|---|
| Domain | `internal/*/domain/` | None — pure logic |
| Application | `internal/*/application/` | In-memory fakes only |
| HTTP handlers | `internal/*/http/` | In-memory fakes via `app.Test()` |

**All tests must pass before a PR can be merged.** No real database is required to run the test suite.

## Code Style

This project follows standard Go conventions with a few additions:

- **DDD layering is strict.** Domain packages must not import application or infrastructure packages. Infrastructure must not import HTTP packages.
- **No ORM.** Use sqlc-generated queries only. If you add a SQL query, run `sqlc generate` and commit the generated files.
- **No comments explaining what the code does** — use clear naming instead. Comments are only for non-obvious *why*.
- **No error handling for impossible cases.** Trust internal guarantees; only validate at system boundaries.
- **Tests use in-memory fakes**, not mocks generated by gomock (unless testing an interface contract).

Run the linter before pushing:

```bash
make lint
```

## Submitting a Pull Request

1. **Fork** the repository and create your branch from `main`:
   ```bash
   git checkout -b feat/your-feature-name
   ```

2. **Write tests first** (TDD) — new behavior must be covered.

3. **Ensure all tests pass** and the linter reports no issues.

4. **Update `CHANGELOG.md`** under `[Unreleased]` with a brief description of what changed.

5. **Open a pull request** against `main`. Fill in the PR template — incomplete PRs may be closed without review.

6. A maintainer will review your PR. Be prepared for feedback and iteration.

## Commit Message Format

Follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <short summary>
```

**Types:** `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `ci`

**Examples:**

```
feat(dictionary): add full-text search endpoint
fix(identity): correct token expiry comparison
docs(readme): update getting started steps
test(community): add vote idempotency test
chore(deps): bump gofiber to v2.52.6
```
